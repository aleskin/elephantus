# AGENTS.md — Circus Elephant (elephantus)

Семейная игра про циркового слоника. **Автор идеи и геймдизайнер — Полина (8 лет).**
Владелец (папа) отвечает за технику, архитектуру и часть решений. AI-агент — технический
помощник: превращает идеи Полины в задачи и пишет весь код.

Концепция и все игровые решения — в `SPEC.md`. Задачи — в `TODO.md`.

---

## 🧭 НОВАЯ СЕССИЯ — НАЧНИ ЗДЕСЬ

Этот файл написан так, чтобы новый агент мог продолжить работу **без объяснений владельца**.

### Кто есть кто
| Кто | Роль | Как с ним работать |
|---|---|---|
| **Полина**, 8 лет | автор игры, решает всё про то, как играется игра | её идеи приходят голосом через папу; говорить с ней простыми словами, без техники |
| **Владелец** (папа) | техника, архитектура, переводит Полину | пишет по-русски, мыслит вслух, идеи приходят по кусочку; доверяет агенту — не просит ревью, хочет, чтобы агент сам делал и коммитил |
| **Агент** | разбивает на задачи, пишет код, проверяет, коммитит | не придумывает игру за Полину |

### Игра в двух словах
Цирковой слоник идёт по арене и перепрыгивает обручи; в прыжке может сделать сальтуху; в
конце уровня — кубок за суперпрыжок. 2.5D: объёмные модели, камера сбоку, движение в одной
плоскости. Godot 4.7 + типизированный GDScript. Подробно и точно — `SPEC.md`.

### Порядок чтения в начале сессии
1. Этот файл целиком.
2. `SPEC.md` — что уже решено («Согласовано»), что Полине важно, что открыто.
3. `TODO.md` — доска сверху: что в работе, что открыто, что ждёт ответа.
4. `git log --oneline | head -20` — что сделано недавно.
5. `inbox/` — есть ли неразобранные голосовые (папка вне git).

### Типовые сценарии

**А. «Полина сказала вот что…» / «вот голосовое» / файл в `inbox/`**
1. Разобрать по правилам раздела «🎤 Голосовые Полины» (корзины: ответ / идея / меняет
   согласованное / важно учесть / не про игру).
2. Обновить `SPEC.md` и `TODO.md`: ответы закрывают вопросы `❓`, идеи становятся задачами,
   большие идеи — разбить на маленькие задачи (каждая ≤ 8 часов, с понятным результатом).
3. Коммит `docs(todo): ...` (без номера CEL), если менялись только `TODO.md`/`SPEC.md`.
4. Короткий отчёт владельцу: что понял, какие задачи создал, что непонятно (вопросы для Полины
   — готовыми фразами, которые папа может ей зачитать).
5. Если после разбора есть задачи без блокеров и правила для них согласованы — **сразу брать
   в работу** (сценарий Б), не дожидаясь отдельной команды. Если всё упирается в вопросы к
   Полине — остановиться и сказать, какие ответы нужны.

**Б. «Делай» / «продолжай» / без конкретной задачи**
1. Взять из `TODO.md` первую задачу со статусом `Открыта` (или `В работе`), у которой нет
   блокеров и нет открытых вопросов `❓` в зависимостях.
2. Статус → `В работе`; короткий план и файлы → сделать → проверки → `✅ Выполнена` → коммит.
3. Следующая задача — так же. Останавливаться, когда упёрлись в решение Полины или владельца.

**В. Готов играбельный шаг**
Сказать владельцу, что именно Полине попробовать в игре и о чём её спросить после (1–3 простых
вопроса). Её реакцию потом разбирать как голосовое (сценарий А).

### Когда спрашивать, а когда делать самому
- **Сам:** вся техника — структура кода, сцены, имена, инструменты, порядок задач, коммиты.
- **Спросить владельца:** новые зависимости/плагины, смена движка или подхода, что-то
  необратимое, изменение уже согласованного правила.
- **Спросить Полину (через папу):** всё, что меняет, как играется игра — кнопки, правила
  прыжков, что бывает при ошибке, как выглядит слоник, как выдаётся кубок.
- Неизвестное игровое число нужно, чтобы двигаться дальше, — временное значение в настройках с
  `TODO(CEL-XXXXX)`, а вопрос — в `TODO.md`. Работа не стоит, но решение остаётся за Полиной.

## 🚨 ГЛАВНЫЕ ПРАВИЛА

1. **Это игра Полины. Не придумывай игровые правила.**
   Всё, что влияет на механику (кнопки, прыжки, обручи, кубок, проигрыш), берётся только из
   раздела «Согласовано» в `SPEC.md`. Неизвестное — вопрос в `TODO.md` (статус `❓ Нужен ответ`)
   и варианты на выбор, а не произвольное значение в коде.
2. **Неизвестные числа — в настройки, не в код.** Скорость, высота прыжка, интервал между
   нажатиями и т.п. выносятся в одно место с настройками и помечаются `TODO(CEL-XXXXX)`.
3. **КОММИТ ПРИ ЗАВЕРШЕНИИ ЗАДАЧИ CEL. PUSH ЗАПРЕЩЁН.**
   Одна задача — один коммит. `git push` делает только владелец. Не коммитить вместе с задачей
   посторонние незакоммиченные изменения.
4. **ДЕЛАЙ РОВНО ТО, ЧТО ПРОСИЛИ.** Маленькие законченные шаги, без «улучшений» и абстракций
   «на будущее». Перед крупным шагом — короткий план и список затрагиваемых файлов.
5. **Не утверждай, что игра запускается, если не запускал.** После каждого шага — сообщить, что
   проверено, а что нет.
6. **Не монолит.** Раздельно: управление игроком, состояние слоника (явные состояния), обручи,
   уровень, интерфейс, настройки. Временные модели легко заменить моделями из Blender.

## 📝 КОММИТЫ — СТРОГО

```
[CEL-XXXXX] BF <module>: <short English description>   ← исправление бага
[CEL-XXXXX] <module>: <short English description>       ← новое / улучшение
```

| Поле | Значения | Примечание |
|---|---|---|
| `CEL-XXXXX` | номер задачи, 5 цифр с нулями | обязателен для изменений кода |
| `BF` | только для багфиксов | для фич не пишется |
| `<module>` | `player` / `hoop` / `level` / `camera` / `input` / `ui` / `art` / `build` / `docs` | основная затронутая часть |
| `<description>` | английский, повелительное наклонение, ≤72 символа | без точки в конце |

- Сообщения коммитов **только на английском**. Без строк об авторстве Claude/Anthropic/AI.
- `docs(...)` / `chore(...)` коммиты — без номера CEL.
- Подзадачи: `CEL-XXXXX-YY`, перечисляются явно под родительской задачей в `TODO.md`.

## 📋 СИСТЕМА ЗАДАЧ (как в dji_tello_cli / panorama-ai)

| Файл | Назначение |
|---|---|
| `TODO.md` | текущий спринт: доска (сверху) + детали задач (снизу), максимум **30** открытых задач |
| `TODO-next-sprint.md` | бэклог: идеи и отложенные задачи |
| `SPEC.md` | концепция игры: что согласовано, что ещё открыто |

- **Next Task ID** — строка `## ⚡ Next Task ID: CEL-XXXXX` в `TODO.md`, единственный счётчик.
  Берём номер, в той же правке увеличиваем счётчик. Номер никогда не используется повторно.
- Блок задачи:
  ```
  ### [CEL-XXXXX] <module>: <название>
  - **Status:** Открыта
  - **Complexity:** 3
  - **Description:** ...
  ```
- **Статусы (точно так):** `Идея`, `Открыта`, `В работе`, `✅ Выполнена`, `❓ Нужен ответ`,
  `❗ Требует действий владельца`, `Заблокирована`, `Закрыта (<причина>)`.
- `❓ Нужен ответ` — вопрос по игре или по технике. В задаче обязательно поле
  `- **Решает:** Полина` или `- **Решает:** владелец`. Когда ответ получен — записать его в задачу
  (словами того, кто ответил), перенести решение в `SPEC.md` → «Согласовано», задачу закрыть.
- Готово = `- **Status:** ✅ Выполнена` и всё. Выполненные задачи руками не удалять.
- **Complexity** = часы по Фибоначчи: 1, 2, 3, 5, 8, 13, 21, 34, 55 (округлять вверх).
- Больше 30 открытых задач в `TODO.md` → начинать каждый ответ с
  `⚠️ ГОРШОЧЕК НЕ ВАРИ! Открытых задач в TODO.md: N/30.`
- Задача, которую пока нельзя сделать или понять, уходит в `TODO-next-sprint.md` с причиной.
- Доска сверху `TODO.md` обновляется вместе с деталями задач.

**Чек-лист завершения задачи:** сделать → проверки зелёные → статус `✅ Выполнена` в `TODO.md`
(и `SPEC.md`, если поменялись правила) → коммит.

## 🎤 ГОЛОСОВЫЕ ПОЛИНЫ

### 🔒 Что НЕ попадает в репозиторий — никогда
- Аудиофайлы, расшифровки голосовых, дословные цитаты из них.
- Исходный промпт проекта и вложения (`.zenflow-attachments/`).
- Личное: имена других людей, школа, адреса, всё, что не про игру.

В репозитории — **только уже разобранные задачи** и решения в `SPEC.md`, пересказом своими
словами (русский или английский). Её слова-термины для игры можно оставлять («сальтуха»).

### Где лежат голосовые
- Папка `inbox/` в корне проекта — в `.gitignore`. Туда кладутся аудио (`*.wav`, `*.ogg`, …) и
  расшифровки (`*.txt`, рядом с аудио, то же имя).
- Расшифровку может сделать другой агент или локальная расшифровка (CEL-00020).
- После разбора — удалить файлы из `inbox/` после подтверждения владельца.

### Как читать расшифровку — Полине 8 лет
- Текст **несвязный**: перескакивает с темы на тему, фразы не закончены, повторы, фантазии,
  «ну... это... короче». Читать **по смыслу**, не буквально.
- Расшифровка детской речи содержит **ошибки распознавания** — странное слово чаще всего
  ослышка. Подбирать похожее по звучанию и подходящее по смыслу игры; не угадывается — вопрос.
- Голосовое — **не обязательно ответ** на наш вопрос. Это может быть новая идея, рассказ, что ей
  понравилось или не понравилось, или вообще не про игру.
- На фоне могут звучать другие люди — учитывать только Полину (и владельца, если он явно
  поясняет).

### Разбор: каждый кусок — в одну из корзин
| Корзина | Что делаем |
|---|---|
| **Ответ** на открытый вопрос `❓` | Записать ответ пересказом в задачу; ясно → решение в `SPEC.md` → «Согласовано» с пометкой `(голосовое YYYY-MM-DD)`, задачу закрыть |
| **Новая идея** для игры | Новая задача со статусом `Идея`: что она хотела (пересказ) / как мы это поняли / что предлагаем |
| **Меняет согласованное** | Не менять `SPEC.md` молча: задача `❓ Нужен ответ`, `Решает: владелец` — подтвердить, что Полина правда передумала |
| **Важно учесть** (что нравится, что страшно, что сложно, любимые цвета, на чём играет, какой рукой) | Пересказ в `SPEC.md` → «Что важно Полине» |
| **Не про игру** | Пропустить, никуда не записывать |

- Не уверен в смысле — **не записывать как согласованное**. Один короткий вопрос понятными
  ребёнку словами (`❓ Нужен ответ`, `Решает: Полина`), без технических слов.
- Не придумывать за неё и не «улучшать» идею. Не принимать технические решения вместо неё, если
  они меняют то, как играется игра.
- Отчёт владельцу после разбора: «в голосовом от <дата>: N ответов, M идей, K важного, X
  непонятно» + список созданных/изменённых задач. Затем — вопрос, можно ли удалить файлы.

## 🛠️ СБОРКА И ПРОВЕРКИ

**Godot 4.7.x + GDScript со строгой типизацией** (решение и рейтинг — CEL-00002).
- Только API Godot 4.x. Не использовать API и примеры Godot 3 (`KinematicBody`, `yield`,
  `onready var` без `@`, `export var` без `@` и т.п.).
- Типы везде: у переменных, параметров, возвращаемых значений. Нетипизированный код — ошибка.
- Без плагинов из Asset Library без отдельного решения.
- Команды `make run` / `make check` / `make lint` появятся в CEL-00004; установка — CEL-00003.

Окружение владельца: Ubuntu, у агента нет `sudo`. По возможности — совместимость с Windows.
Зависимости и плагины — только при необходимости и после согласования.

## Стиль работы владельца
- Общение на русском; `TODO.md` / `SPEC.md` — на русском; код, комментарии, коммиты — на английском.
- Идеи приходят постепенно — сначала записать задачей, реализовывать после подтверждения.
- Объяснять решения простым языком: игру делают вместе с ребёнком, важны наглядность и
  возможность экспериментировать (поменять число — увидеть результат).
